# 整包退回接管未结复验的方案复审

状态：2026-10-20 追加权限复审发现的三个缺口已修复，并完成原发起人停用、继任恢复、active 转派、连续整包退回及独立正常包的真实 API 回归；已按用户授权提交 main PR，后由用户账号在 GitHub 外部合并；本会话未执行合并或生产部署。当前 Gate、部署和验收证据以文末链接为准；浏览器截图仍待补齐。

**Why:** 停止旧 Sand 复验并不自动转移旧整改责任。旧责任继续阻断新流程可能形成循环等待，强行关闭又可能制造通过结论；持久化接管字段还会影响旧 worker 的解析和恢复。

**How to apply:** 实施前明确精确责任范围和接管授权、新 Sand 正式结果如何收口旧责任、并发决定与保存的统一围栏、每阶段幂等恢复、旧问题必检与合法待定、混合版本及回滚兼容。首版建议限于供应商整改正式完成而 Sand 复验未结束的完整覆盖范围。这是评审时的约束，不能据此跳过现有生产阻断。候选实现边界见文末核验指针。

## 第二轮补充复审（2026-10-20）

**Why:** 原复审还需区分预览与执行授权、决定已落地与实际派出自查、报告写入与答案代改写入。连续整包退回及撤销若无明确语义，也可能使责任链丢失或旧轮次被重启。

**How to apply:** 沿同一完整复审清单核验权限绑定、可接手负责人及失资格质检员的重新分派、旧页面和延迟代改写入守卫、跨代接管关系与旧问题覆盖，以及关闭弹窗/发布回滚/业务撤销的区别。上述均为待实施方案约束，不当作已确认生产漏洞；首版建议不开放一键撤销。


## 用户确认的终止边界（2026-10-20）

用户明确要求：被终止的对象及其下属流程应全部进入不可业务操作态，不得再分配质检或由后台恢复推进。此要求适用于终止生效后的前端、服务端、自动派单和恢复入口；保留历史及审计只读查看，必要技术清理不得恢复业务执行。

整包退回与终止整个数据包需要在方案中分开：退回可以依据明确的新退回决定创建新一轮自查，但已停止的旧轮次仍永久只读，不能重派或被复活；终止整个包则不得继续创建自查、整改、复验等后续任务。前文“旧任务停了，新自查无人接”的接收能力检查仅属于整包退回路径，不适用于终止包。

并发边界：终止与已在途保存/交卷/代改/派单必须有明确先后；终止生效后旧请求不得继续推进流程。按钮置灰不足以验收，需覆盖直接 API、旧页面、延迟请求和恢复 worker。此为用户确认的目标规则，不代表本次已验证或修复当前实现。

**Why:** 本次源码核验仍有整包准入 mixed DML 跨表事务与 Sand 保存跨表围栏条件。缩短超时不等于物理锁隔离；模拟回归通过也不证明其他正常包无业务影响。

**How to apply:** 沿 [2026-10-20 代码审计与锁约束](/Users/leslie/.codex/visualizations/2026/10/20/01a15791-b458-7e83-a099-1620fc10895e/package-return-code-audit.md) 核对冻结 SHA、7 项离线用例和入口边界。接管计划、旧代次写准入、在途收敛、幂等恢复与常规包性能一起设计；禁止把范围遍历、来源 RPC 和整批派单塞进持锁事务，也不能无替代协议直接删围栏或只用 Redis 锁。测试环境用真实 Hologres 计划/锁等待与不同包 p95/p99 对照验收，不做生产压测。该节记录实施前的审计结论，后续候选实现见文末；没有验收或修改生产。

## 用户纠正：整包退回不以人工报告为前置（2026-10-20）

用户明确：质检员随机看两题发现完全不达标即可整包退回；包内所有批次都进入供应商重新处理，不因是否派检、检查或提交人工报告而排除。这是整包退回的业务规则，覆盖前文以“已提交人工质检报告交原质检员自查”为统一前提的方案限制。

**Why:** 现实现将整包退回耦合为已有人工报告的重检，要求当前 SPACE_QC 报告为 submitted；因此明明保留历史报告、但当前已进入 active 新轮次的包也会显示“缺少完整的人工质检报告”。这不是要求用户补完当前检查的合理业务门槛。只删除报错条件仍会撞上依赖原报告的准备、授权、转派和责任闭环代码。

**How to apply:** 整包退回决定直接冻结完整批次范围、当前权限和原因；有检查记录保留历史并停止旧轮次，无检查记录也建立真实供应商待处理工作，不伪造原报告。沿源码追完整的供应商后续路径和重新交接，不把“请求返回成功”当作已完成返工。已有责任、旧恢复和新验收分别核验，保留逐包并发保护。用户后续已明确为供应商全量质检：每条作答逐条判定并提交质检报告，不是标注员逐题重新提交。普通派检和单批退回继续原规则。

## 最终口径：仅整包退回触发供应商全量质检（2026-10-20）

**Why:** “每条作答重新提交”容易被误解为强制标注返工；用户最终明确要生成覆盖全部作答的供应商质检任务。旧人工报告、旧抽样比例和原人员继续在职，都不能变成这次整包质检的业务前置条件。日常质检的规则不能随之改变。

**How to apply:** 仅服务端已生效的整包退回决定触发 100% 供应商质检。无旧任务时创建真实首次质检，有旧任务时停止旧轮次并建立新轮次；逐题判定、报告提交、负责人验收和整包重交分别核验，发现不合格项才进入既有标注整改。旧检查、待恢复命令与责任证书保持只读；接管不能提前关闭旧责任，新整包最终 Sand 验收后按子责任先于父责任收口。新增 intent 字段时保持已保存旧决定的序列化身份，避免升级后无法恢复原围栏。普通首次派检、单批退回和其他包的保存提交另做反例验证。

## 2026-10-22 修复已发布但接管开关未启用

**Why:** 整包退回的新代码与“接管尚未结束的 Sand 复验”是两个生效条件。接管开关关闭时，运行装配不注入持久执行围栏，详情接口也不会声明可接管，前端因此没有相应勾选和预览。此时供应商子责任即使已完成，尚未提交的 Sand 复验仍会让父责任保持未结，普通整包退回继续报 `REVIEW_BLOCKED`。刷新页面不会改变服务端开关或正式责任状态；也不能为了消除阻断而提前关闭旧责任。

**How to apply:** 先对齐 Web、派发与恢复执行器的实际 SHA 和健康副本，再读取进程中的 `package_return_takeover_enabled`、环境注入及运行装配结果；只看 main、PR 合并或镜像版本不足以证明启用。沿真实父子责任、当前 Sand 报告与原生执行投影确认阻断对象。必要时在独立诊断进程中用只读连接执行原生冻结预检，对照开关关闭与仅该进程开启、显式请求接管时的结果，并核对前后决定与责任版本没有变化；此预检通过只证明候选范围可接管，不是生产开关已启用或业务退回已执行。
