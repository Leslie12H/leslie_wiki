# 团队研发与发布规范：Test 验收、Cherry-pick 上线、Main 回合

版本：v1.0｜整理日期：2026-09-17

适用范围：使用独立 test、prod 环境，同时进行需求开发和缺陷修复的项目。本规范依据本次确定的流程整理；分支保护及 CI 自动化需由各仓库落实，不表示已配置完成。

## 1. 目标与基本约定

**Why:** 支持多个需求并行提测、按需独立上线，并确保生产修复和发布改动及时进入测试环境，避免 test 演变为独立代码主线。

**How to apply:** 开发分支合入 test 并部署验收；验收通过的提交 cherry-pick 到基于最新 main 的上线分支，通过 PR 进入 main；main 的所有新增改动通过普通 merge 回合 test，并部署测试环境。

本文“进入 main”指 cherry-pick 后通过上线 PR 合入；“回合 test”指 main → test 的普通 merge。不得整体合并 test 到 main。

```text
最新 main → feature/* 或 bugfix/* → PR 合入 test → 部署 test → 测试通过
                      │                                      │
                      └──── 已验收的明确提交清单 ──────────────┘
                                      ↓ cherry-pick
                         基于最新 main 的 promote/*
                                      ↓ 检查、回归、PR
                                    main → 部署 prod
                                      │
                                      └→ merge 回合 test → 部署 test → 回归
```

## 2. 分支职责

| 分支 | 职责 | 创建来源 |
|---|---|---|
| main | 已验收、可发布的生产代码主线 | 长期保留 |
| test | 多需求集成和测试验收 | 长期保留，持续接收 main 回合 |
| feature/<需求编号> | 单个需求开发及其测试修复 | 最新 main |
| bugfix/<问题编号> | 独立缺陷修复 | 最新 main |
| promote/<需求或批次编号> | 承载准备进入 main 的 cherry-pick 结果 | 最新 main |

main 与 test 禁止直接推送和强推，变更通过 PR。开发分支不得从 test 创建，也不得将 test 整体合回开发分支，以免夹带其他未上线需求。环境差异放在配置与 Secret 中。

## 3. 正常开发、提测与发布

1. **开发自测。** 开发负责人从最新 main 创建独立分支，完成开发、自测和代码评审。一个分支只承担一个可独立交付的需求或问题；跨需求依赖必须声明。
2. **合入 test 并部署。** 提交开发分支 → test 的 PR，注明需求、测试范围、依赖和源提交。合入后部署 test，记录实际运行 SHA；测试负责人确认版本后开始验收。
3. **修复与复测。** 测试发现的问题在原开发分支修复，再通过 PR 合入 test、部署并复测。不得仅在 test 留下修复而遗漏上线提交。test 集成冲突的解决需评审；涉及本需求必要逻辑的调整，必须在上线候选中体现并验证。
4. **冻结验收范围。** 测试通过时记录 test 部署 SHA、开发分支源 SHA 清单、测试结论和遗留项。后续新增提交不自动继承通过状态；已提测提交不得随意改写历史。
5. **Cherry-pick 准备上线。** 从最新 main 创建 promote 分支，按依赖顺序使用 `git cherry-pick -x <源SHA>` 搬运已验收提交，包含测试期间的修复。禁止从 test 随意选取混合多个需求的提交或 merge commit。保留源 SHA 与目标提交映射。
6. **验证实际上线组合。** 对 promote 分支执行构建、自动检查及相关回归。test 中其他未上线需求可能掩盖依赖问题，因此 test 的验收不能替代上线组合验证。发生冲突、缺失依赖或行为差异时，测试负责人必须对最终候选补充验证；必要时预约 test 环境临时部署候选，记录 SHA，验证后恢复 test 分支部署。
7. **合入 main 并发布。** 上线 PR 附齐证据，评审通过后合入 main。若 main 前移，更新候选并重新运行检查；若最终合并结果变化，重新验证实际发布结果。prod 发布绑定确定 SHA/tag 和制品摘要，完成生产冒烟并记录结果。
8. **回合与关闭。** main 合入即触发 main → test 同步 PR，不等待下一批需求。普通 merge 保留主线历史；合入后部署 test 并执行冒烟及受影响回归。生产发布与 test 回合均有结果后，才关闭需求或缺陷。

## 4. Main 回合 Test 的强制规则

- 所有 main 改动都必须回合，包括正常需求、bugfix、hotfix、回滚提交、配置代码及迁移脚本。
- main PR 合入人负责发起和跟踪回合；原开发负责人处理冲突；测试负责人确认影响及回归；发布负责人确认实际部署版本。同一成员可以承担多个角色。
- 回合在 main 变更后立即发起，原则上当日完成，并在受影响需求下一次验收结论出具前完成。紧急生产修复不因 test 回合阻塞而延迟，但阻塞必须记录负责人和预计完成时间，不得标记闭环。
- main → test 使用普通 merge，不使用 squash 或逐条 cherry-pick。Cherry-pick 进入 main 会产生新 SHA，回合出现内容重复或冲突时必须核对语义，不能整批选用 ours/theirs 覆盖另一侧。
- 同步完成包括三件事：代码已回合、test 部署成功、回归有结果。不能只以 PR 已合并作为完成依据。
- 回合后确认被同步的 main SHA 是 test 的祖先，并核对实际代码差异。祖先关系通过只能证明历史包含，不能证明后续代码没有覆盖生产修复。

## 5. 紧急线上修复

紧急 hotfix 可由发布负责人确认后缩短正常验收流程，但仍需 PR 评审、必要自动检查和针对性验证，并记录跳过项目、原因及补测负责人。

正常情况下从最新 main 创建修复分支，修复通过 cherry-pick 上线 PR 进入 main 后发布 prod，再按第 4 节回合 test、部署并补测。

若 main 含尚未发布的其他改动，从实际 prod tag 创建 hotfix 候选并仅发布该候选，避免捆绑其他需求；修复同时通过 PR 进入 main，再回合 test。记录该例外的生产版本与 main 版本，不能假定 main HEAD 等于生产版本。

## 6. Test 环境与差异管理

- 共享 test 环境每次部署记录操作者、来源分支、SHA、需求清单与时间。部署前通知当前测试负责人，验收期间的覆盖部署须协调；版本发生变化后评估受影响测试结论。
- 维护 test 相对 main 的未上线需求清单，每项有负责人和处置状态。每周检查一次：继续验收、准备上线、延期或撤销。
- 延期或取消需求不得无限滞留 test；通过可评审的撤销 PR 清理，并检查依赖、部署和回归。撤销后重新提测需显式恢复变更并测试，不能假定再次合并原分支会自动恢复。
- Cherry-pick 会造成不同 SHA 表达相同改动，不以 ahead/behind 提交数量要求“两分支归零”。应检查 main 历史是否已回合、实际文件差异是否都对应已登记未上线需求；没有未上线改动时，应无未解释的代码差异。
- 数据库迁移、依赖文件、配置变更需纳入发布清单；test 上存在某项迁移不代表 prod 已执行。回滚生产制品后，仍需明确 main 的修复或撤销方案，并同步 test，避免下一次发布重新引入问题。

## 7. 上线与回合检查单

```markdown
- 需求/问题编号：
- 开发负责人 / 测试负责人 / 发布负责人：
- 开发分支与提测 PR：
- test 验收部署 SHA、结果链接：
- 已验收源提交清单（包含测试修复）：
- 依赖需求、数据库迁移与配置变更：
- promote 上线 PR、源/目标提交映射：
- 最终上线组合检查与回归结果：
- main 合入 SHA / prod 发布 SHA或tag / 制品摘要：
- 生产冒烟结果：
- main → test 回合 PR及覆盖的 main SHA：
- 回合后 test 实际部署 SHA及回归结果：
- 未完成项、负责人、预计完成时间：
```

## 8. 仓库执行配置

由仓库维护人落实 main/test 分支保护、必需检查、上线 PR 模板，以及 main 更新后自动创建或更新回合 PR。同步冲突或部署失败必须可见；自动化未落地前，由 main PR 合入人按同一规范手动执行。

规范完成不代表流水线已实施。实施时按仓库实际合并方式核验源提交追踪、回合祖先检查、部署 SHA 与 CI 门禁。
